# Insurance Hub — microservices build skill

You are implementing an enterprise-grade Spring Boot microservices system from a bank's
Insurance Hub API specification. Insurers (TSPs) call ONE external API; we split the work
across three services behind it.

The developer is learning microservices while building this. After every phase, stop and
give a short summary: what was built, the 2–3 key design decisions and why, and what to
review. Do not silently race through several phases.

## Architecture (do not change without an ADR)

```
Insurer (TSP) --HTTPS + OAuth2 + JWS/JWE--> hub-gateway :8080
                                              | routes by appStatusCode
                          +-------------------+-------------------+
                          v                                       v
                 policy-service :8081   <--coverage lookup--  claims-service :8082
                 01 create, 02 renew                          03 register, 04 status
                 policy_db (MySQL)                            claims_db (MySQL)
                          |                                       |
                          +------ outbox -> Kafka topics <--------+
```

| Module | Responsibility | Owns |
|---|---|---|
| `hub-gateway` | OAuth2 resource server, IP allowlist, JWS verify + JWE decrypt, request validation, route by `appStatusCode`, map external DTO -> internal API, encrypt + sign response, audit | `gateway_db.request_audit` |
| `policy-service` | New policy (01), renewal (02), coverage lookup for claims | `policy_db` |
| `claims-service` | Claim registration (03), claim status update (04) | `claims_db` |
| `hub-common` | Tiny shared library: `HubResponse`, `HubErrorCode`, header constants, PII masking, MDC/correlation filter | nothing |

Why hub-gateway is a Spring MVC app and not Spring Cloud Gateway: the routing key sits
inside an encrypted body, so we must decrypt before routing. The gateway is also the
anti-corruption layer: the bank's all-String, `DD/MM/YYYY` contract lives only there.
Internal APIs use proper types (`LocalDate`, `BigDecimal`, enums).

## Non-negotiable rules

1. **Database per service.** A service never reads or writes another service's schema.
   Cross-service data comes via internal REST or Kafka events. Each service gets its own
   DB user that can only access its own schema.
2. **`hub-common` stays tiny.** No entities, no domain logic, no service-specific DTOs.
   If you're tempted to share a domain class, duplicate the DTO instead. Shared domain
   code couples deployments.
3. **Idempotency on `(inspId, reqId)`.** Insurers retry. A repeated request must return the
   original `txnId` and must not create a second record. Enforce it with a unique constraint
   in each domain service's `processed_request` table, not just a check in code.
4. **Never log raw payloads or PII.** Mask `cif`, `accountNum`, `loanAcctNum`, `mobileNum`,
   `name`, `address` with `PiiMasker` from hub-common. Never log the `enc` string or any key.
5. **Logs are centralized, never local.** Apps write JSON to stdout only; the platform ships
   them to CloudWatch Logs (one log group per service, explicit retention, KMS-encrypted).
   Every line carries `txnId` so one query traces a request across all services.
6. **No secrets in the repo.** Keys, client secrets and DB passwords come from env vars
   locally and AWS Secrets Manager in the cloud. Dev keypairs are generated by
   `scripts/gen-dev-keys.sh` into `./.secrets/` (git-ignored).
7. **Schema changes only via Flyway.** `spring.jpa.hibernate.ddl-auto=validate` everywhere.
8. **Crypto can be bypassed only in the `local` profile**, via `hub.crypto.enabled=false`.
   Add a startup guard that fails the app if crypto is disabled while a `dev`/`prod`
   profile is active.
9. **Versions are pinned in the parent POM only.** Use the latest stable Spring Boot and
   the matching Spring Cloud / Spring Cloud AWS release train. Check compatibility before
   choosing, and record the choice in `docs/adr/0001-tech-stack.md`. Verify configuration
   property names against the docs for the Boot version you picked, because some
   observability properties were renamed between major versions.
10. **Ask before adding new infrastructure** (a new datastore, broker, framework or paid AWS
   service). Small libraries are fine.

## Tech stack

Java 21 (17 minimum), Maven multi-module, Spring Boot (Web, Validation, Data JPA,
Security OAuth2 Resource Server, Actuator), MySQL 8 + Flyway, Spring Kafka,
`RestClient` + `@HttpExchange` interface clients for service-to-service calls (not
OpenFeign, which is feature-complete/maintenance mode), Resilience4j, Nimbus JOSE+JWT for
crypto, Micrometer Tracing (OpenTelemetry bridge), springdoc-openapi, Lombok (optional,
records preferred for DTOs), MapStruct for mapping.
Tests: JUnit 5, AssertJ, Mockito, Testcontainers (MySQL, Kafka), WireMock, ArchUnit.
Quality: Spotless (google-java-format), JaCoCo, Trivy or OWASP dependency-check in CI.
Local infra via Docker Compose: MySQL, Kafka (KRaft), Keycloak, `grafana/otel-lgtm`.
AWS: ECS Fargate, ECR, ALB, RDS MySQL, MSK, Secrets Manager, Parameter Store, CloudWatch
(Logs, Logs Insights, alarms, dashboards, Container Insights), X-Ray via ADOT, SNS, KMS, S3.

## Repository layout

```
insurance-hub/
├── pom.xml                      # parent: dependencyManagement, plugins, versions
├── hub-common/
├── hub-gateway/
├── policy-service/
├── claims-service/
├── docker-compose.yml           # infra + services
├── docker/                      # mysql init (schemas + users), keycloak realm export
├── scripts/                     # gen-dev-keys.sh, send-sample.sh (encrypt + call)
├── infra/terraform/             # AWS (phase 9)
├── .gitlab-ci.yml
├── docs/
│   ├── adr/                     # architecture decision records
│   ├── progress.md              # phase checklist, updated at end of each phase
│   └── open-questions.md        # spec gaps to confirm with the bank
└── CLAUDE.md
```

Package layout inside each service (`com.insurancehub.<service>`):

```
api/             controllers, request/response DTOs, exception handler
application/     use-case services (@Transactional boundaries live here)
domain/          entities, value objects, domain rules, domain exceptions
infrastructure/  persistence (repositories), messaging (outbox, Kafka), clients (HTTP)
config/          Spring configuration, properties classes (@ConfigurationProperties)
```

Dependencies point inward: `api -> application -> domain`, and `infrastructure` implements
ports defined in `application`/`domain`. Enforce this with an ArchUnit test in every service.

## Build order (one phase at a time)

Work through the phases in order. At the end of each phase: `mvn verify` must be green, update
`docs/progress.md`, then stop and summarize for review.

| Phase | Goal | Done when |
|---|---|---|
| 0 | Scaffold: parent POM, 4 modules, Spotless, JaCoCo, compose with MySQL/Kafka/Keycloak/LGTM, CLAUDE.md, ADR-0001 | `mvn verify` green, `docker compose up` all healthy |
| 1 | `hub-common`: `HubResponse`, `HubErrorCode`, `PiiMasker`, correlation filter + auto-config | Unit tests for masker and filter |
| 2 | `policy-service` 01: create policy, Flyway V1, idempotency, internal API, exception handler | Testcontainers IT: create, duplicate reqId, duplicate policyNum |
| 3 | `policy-service` 02 renew + coverage lookup API | ITs for renewal rules and coverage on date |
| 4 | `claims-service` 03 register (calls coverage), 04 status update + history | WireMock for policy-service, ITs for status rules |
| 5 | `hub-gateway`: OAuth2, validation groups per code, routing, mapping, error mapping, audit; crypto off in `local` | E2E with Keycloak token through gateway to both services |
| 6 | `hub-gateway` crypto: JWS/JWE with Nimbus, per-insurer key registry, `send-sample.sh` | Round-trip crypto tests, tampered signature rejected |
| 7 | Outbox + Kafka events in both services | IT: event lands on topic exactly once per business change |
| 8 | Hardening: Resilience4j, JSON structured logs (logstash format), tracing, metrics, readiness probes, Dockerfiles | Trace spans visible gateway→service in Grafana; log-capture test proves txnId present and PII absent |
| 9 | AWS: Terraform (VPC, ECR, ECS Fargate, ALB, RDS, MSK, Secrets Manager) + centralized logging/monitoring (CloudWatch log groups, data protection, saved queries, metric filters, alarms, dashboard, ADOT → X-Ray) + GitLab CI deploy | Sample request succeeds against the ALB in dev AND the "trace one request" saved query shows it across all three services |

## Definition of done for every feature

A feature is done only when all of these are true: unit tests cover the domain rules;
at least one Testcontainers integration test hits the real endpoint and database; the
Flyway migration is added (never edit an applied migration); every failure maps to a
`HubErrorCode`; logs carry `traceId`, `reqId`, `inspId`, `txnId` and contain no unmasked
PII; the OpenAPI description is accurate; and any spec ambiguity you hit is recorded in
`docs/open-questions.md` with the assumption you made.

## When the spec is unclear

The spec is incomplete: status value lists, respCodes for crypto failures and some
validation rules are not finalized. Do not invent silent behaviour. Choose the safest
reasonable default, make it configurable where cheap, and log it in
`docs/open-questions.md`. Known gaps are listed in `references/api-contract.md`.

## Commit and review style

Use Conventional Commits (`feat(policy): add renewal endpoint`). Keep one logical change
per commit. In every phase summary, explain *why* for non-obvious decisions in 2–3 lines.
The developer is here to learn the reasoning, not just get the code.
