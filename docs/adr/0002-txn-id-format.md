# ADR-0002: txnId format

Status: Accepted (phase 1)

## Decision

`txnId` is a ULID: 48-bit millisecond timestamp + 80-bit randomness, Crockford Base32-encoded
to a fixed 26 characters, lexicographically sortable by generation time. Generated by
`hub-common`'s `CorrelationFilter` (via a package-private `Ulid.generate()`), only at
`hub-gateway`'s entry point — see `docs/adr/0001-tech-stack.md` and `service-design.md` §4 step
1 ("`CorrelationFilter` (hub-common) sets up MDC and assigns txnId"). `api-contract.md` §4
specifies a ULID explicitly; this satisfies that literally, not just "a random id."

**Implementation is hand-rolled, not a third-party library.** `java.util.UUID` has no ULID or
UUIDv7 support (`randomUUID()` is v4, not time-ordered), and encoding a fixed 128-bit value to
Crockford Base32 is ~30 lines with no runtime dependencies beyond the JDK — not worth a new
Maven dependency (CLAUDE.md rule 10: ask before adding new infrastructure; a well-tested
one-file utility with its own unit tests doesn't reach that bar the way a library would).
Randomness comes from `ThreadLocalRandom`, not `SecureRandom` — this is a correlation id, not
a security token or a key, so cryptographic strength isn't needed, and `SecureRandom` carries a
real (if now rare) entropy-pool-blocking risk on a startup/health-check-sensitive path, which is
exactly the kind of thing phase 0 spent real effort making reliable.

## Schema consequence for phase 2

Every `txn_id` column (`processed_request.txn_id`, `policy_term.txn_id`, and the equivalent
columns in claims-service's schema per `service-design.md` §2/§3) should be **`CHAR(26)`**, not
a wide `VARCHAR`. ULIDs are always exactly 26 characters, so a fixed-width column is both more
space-efficient and self-documenting — a `VARCHAR(N)` would silently invite `N` to drift from
26 with no signal. This is distinct from the `VARCHAR(512)` guidance in `service-design.md` for
PII columns (`cif`, `account_num`, etc.), which is wide on purpose for future at-rest-encryption
headroom — `txn_id` has no such reason to be wide.

## Consequences

- If a future phase needs the JDK's own random UUID for something else (e.g. an `eventId` for
  outbox events, per `service-design.md` §5's event envelope), that's an unrelated decision —
  `UUID.randomUUID()` remains perfectly fine there; this ADR only concerns `txnId`.
- `Ulid.encode(long, byte[])` is package-private and covered by unit tests (all-zero vector,
  timestamp ordering, 26-char/alphabet shape) rather than exhaustively verified against the
  reference ULID spec's test vectors — acceptable for a correlation id, would not be acceptable
  if this were used for anything security-sensitive.
